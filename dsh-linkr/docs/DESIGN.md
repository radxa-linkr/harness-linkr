# dsh-linkr — design

A DeepSeek Harness plugin that turns a **Linkr KVM-over-IP device** into the agent's eyes and hands
on the controlled host computer, plus a live screen panel in the Web UI's right column for the
person. This document is the current design; `docs/CONTRACT.md` is the append-only build journal
(rounds 1–9) that produced it.

## Pieces

```
                    Harness (Node 22, profile-installed bundle)
┌──────────────────────────────────────────────────────────────────────┐
│ index.js            name / inject / Config / apply — wiring only     │
│ host/config.js      defaults, normalisation, Config standard-schema  │
│ host/client.js      the one LinkrClient lifecycle, capture dir, status│
│ host/activity.js    bounded ring of what the agent did + SSE + /log  │
│ host/routes.js      /linkr/* (state, config, connect, input, mjpeg…) │
│ host/tools.js       linkr_status, linkr_computer_use, linkr_panel    │
│ lib/                materialized copy of ../../core (generated by     │
│                     scripts/sync-core.mjs; never edit by hand)        │
│ client.js           Web half: right-column 「电脑」 tab (picture,     │
│                     pointer/keyboard, paste, settings, activity list)│
└──────────────────────────────────────────────────────────────────────┘
        │ HTTPS-ish JSON (login, WHEP)          │ ws://…/ws/media
        ▼                                       ▼
┌──────────────────────────────────────────────────────────────────────┐
│ Linkr device (fw 1.6.0): /api/*, /linkr/info, /ws/media (ws-media)   │
│   captures the host's HDMI and injects USB HID (keyboard/mouse)      │
└──────────────────────────────────────────────────────────────────────┘
        │ HDMI in / USB out
        ▼
   controlled host computer
```

The transport source of truth is the repository-level `core/` (shared with the MCP server); the
plugin ships a copy materialized into `lib/` so a packed tarball is self-contained. One
`LinkrClient` per plugin instance is shared by the tools, the HTTP routes and the panel: one media
socket, one video-mode switch, one input path.

## Device protocol (measured, fw 1.6.0)

- `POST /api/account/login` `{username, passwd: sha256("RADXA_FIXED_SALT_v1"+password)}` → Bearer
  token; auth failures are HTTP 403 `{"code":403,"message":"No Permisson"}`.
- `POST /api/rtc/whep {offer:"ws_mjpeg"|"ws_h264"}` → opaque `answer`; connect
  `ws(s)://<device>/ws/media?authorization=<answer>` with subprotocol `ws-media`.
- MJPEG mode (`video_codec: 1`): one complete JPEG per binary message.
- H.264 mode (`video_codec: 2`): one ws-media packet per message —
  `[type:1][pts:i64][duration:u64][payloadSize:u64][AnnexB payload]`; the Host pipes payloads
  through one ffmpeg child and splits its stdout into JPEG frames.
- Input rides the same socket as `[1-byte type][protobuf]`: keyboard `1` `{state,key,code}`, mouse
  `2` `{mouse_type,buttons,absX,absY,relativeX,relativeY,wheelV,wheelH}` (absolute coordinates are
  normalized 0..1 of the frame; `buttons` bit 1 = left, bit 2 = right).
- H.265 is only offered over WebRTC by this firmware; every WebSocket offer is refused in mode 3.
- An API key from the device UI cannot authenticate `/api/*`.

## Session model

- A session is a media socket plus (optionally) a device video-mode change. The plugin remembers the
  device's original `video_codec` and **restores it** on idle stop, explicit stop, error and dispose.
- `manageVideoMode: false` forbids writing the device setting; a session then only starts if the
  device is already in the wanted mode.
- `codec: auto` prefers H.264 when ffmpeg is found, else MJPEG; a decode failure falls back to MJPEG
  for the rest of the session and says so once (`state.notice`).
- Explicit stop is sticky: after `POST /linkr/disconnect` the live route and the frame route answer
  `409` until `POST /linkr/connect` or an agent action, so a retrying `<img>` cannot quietly revive a
  session someone released. `linkr_status` is read-only and never clears the stop.
- `idleStopMs` (default 120 s) stops an unused session and kills the decoder.

## Agent tools

| Tool | Purpose |
| --- | --- |
| `linkr_computer_use` | computer-use style: `capture` (JPEG returned **inline** as an image block, also written to disk), `click`, `double_click`, `right_click`, `drag`, `scroll`, `type` (ASCII), `key`, `wait`, `paste` (Unicode via the Linkrd clipboard, then `ctrl+v`), `clipboard` (read the controlled machine's clipboard back); `capture_after` on any action; coordinates are pixels of the captured frame. |
| `linkr_status` | device identity, codec/decoder, fps, session and panel state — read-only. |
| `linkr_panel` | open / focus / close the panel tab. |

## HTTP routes (same-origin guarded; prefix `/linkr`)

| Route | Purpose |
| --- | --- |
| `GET /linkr/state` | session state for tools and panel (includes `stopped`, `codec`, `decoder`, `notice`). |
| `GET/POST /linkr/config` | read (password masked) / persist settings through the Harness config editor; the password goes to the `linkr/device` credentials record. |
| `POST /linkr/connect`, `POST /linkr/disconnect` | explicit session control. |
| `GET /linkr/live.mjpeg` | `multipart/x-mixed-replace` of the newest JPEG at `streamFps`. |
| `GET /linkr/frame.jpg` | newest frame as a single response. |
| `POST /linkr/input` | the panel's input path (mouse, key, text) — same client method as the tool. |
| `GET /linkr/panel/stream` | SSE: panel actions (`type:"panel"`) and agent activity (`type:"log"`), with a small backlog. |
| `POST /linkr/panel` | publish an `open` / `focus` / `close` action. |
| `GET /linkr/log?since=` | the activity ring (last 100), for a reader that missed the stream. |
| `GET/POST /linkr/clipboard` | Linkrd clipboard availability / write text and press the paste keys. |

## Panel (`client.js`)

Right-column tab **电脑** with a **Linkr 共享电脑** card: the live picture (top-aligned under the
controls), pointer mapping through the rendered content box, focusable keyboard surface, 连接/断开,
刷新画面, 适应宽度, 设置, 打开 Linkr (device console in a new tab), 粘贴 (clipboard, with a textarea
fallback), and the **最近活动** list of what the agent did. Presentation follows host conventions:
`--dsw-alias-*` tokens only, `dsh-linkr-` class prefix, React from the browser module table.

## Clipboard (Linkrd)

ASCII typing goes through HID; for anything else the plugin writes text to the controlled machine's
clipboard through the device's **control** WebSocket (`/ws`, protobuf `WsMessage`, messages
19/20 for status and 42–45 for read/write) and then presses the host's own paste shortcut
(`ctrl+v`, or `ctrl+shift+v` in a terminal). This needs **Linkrd** running on the controlled
machine; the panel shows availability and never displays clipboard text from the probe. Revisions
are uint64 decimal strings compared as BigInt — never as JS numbers.

## Activity log

A bounded ring (100) of `{at, source, action, detail, ok, params}` for **agent** operations only;
host lifecycle rows (`session`, `device`, `error`) come from the plugin. A person's clicks,
connect/disconnect and config writes are deliberately not recorded. Entries are published on the
panel SSE channel and queryable via `/linkr/log`. Details are single-line, password-redacted and
never carry tokens or frame bytes.

## Configuration

| Key | Default | Meaning |
| --- | --- | --- |
| `baseUrl` | `http://linkr.local` | device origin |
| `username` | `admin` | device account |
| `password` | `''` | empty = use the `linkr/device` credentials record (preferred) |
| `codec` | `auto` | `auto` / `mjpeg` / `h264` |
| `ffmpegPath` | `''` | empty = `$FFMPEG_PATH` → `/opt/homebrew/bin/ffmpeg` → PATH |
| `jpegQuality` | `4` | ffmpeg `-q:v` for the H.264 path, 1 (best) … 10 (smallest) |
| `manageVideoMode` | `true` | switch the device mode while live and restore afterwards |
| `streamFps` | `20` | frames handed to the panel, 1–60 (MJPEG source caps ~37) |
| `idleStopMs` | `120000` | idle stop |
| `screenshotDir` | `''` | capture directory, resolved against the session working directory |

Secrets: the password is read from the Harness credentials record when present; the config file
never receives it, and `/linkr/config` only ever returns `••••••`.

## Security notes

- The routes can type into a real machine: treat the page as a remote control. Cross-origin callers
  are rejected.
- Screen content is untrusted data; tool descriptions tell the model not to follow instructions that
  appear on the host.
- A pressed chord is released in reverse order; an abandoned drag is released; stopping a session
  kills the decoder.

## Testing

- `node --test test/*.test.mjs` — transport unit tests: HID golden vectors, ws-media packet parsing,
  ffmpeg discovery, MJPEG/H.264 sessions against a fake device, locale consistency.
- `node test/host-smoke.mjs` — the Host half against a ctx stub and the fake device: every route,
  every tool action, config/credentials persistence, explicit stop, activity ring/SSE, disposal.
- `LINKR_SMOKE=1 … node --test test/smoke.mjs` — opt-in real-device smoke: login, capture, input,
  and the video-mode restore assertion.

## Known limitations

- **H.265**: not reachable over WebSocket on fw 1.6.0 (WebRTC only); the plugin does MJPEG and H.264.
- **Typing is ASCII**: the device types through a US-layout HID keyboard; a non-ASCII character is
  refused by name (the device's own `/api/paste` silently drops it). Use `paste` for Unicode, which
  needs Linkrd on the controlled machine.
- **One device per plugin instance**; the configuration is a single `baseUrl`.
- **One media consumer at a time** is the device's own constraint: while the plugin holds a session,
  other clients see the device in that mode (restored when the session stops).
- The panel's rendering is not covered by automated tests (no browser automation in this setup).
